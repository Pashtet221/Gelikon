# Номера новых заказов и Т-Банк 3.0.7

Адаптер рассчитан на присланный архив `tbank-woocommerce.zip`, версия 3.0.7.
Файлы плагина не изменяются.

## Что обнаружено в плагине

- `WC_TBank::receipt_page($order_id)` вызывает
  `SupportPaymentTBank::send_data($order, $order_id)`.
- `tbank/SupportPaymentTBank.php`, метод `send_data()`, записывает
  `'OrderId' => (string) $order_id`. Это внутренний ID, а не
  `$order->get_order_number()`: поэтому предыдущий фильтр с `GL-` не влиял на банк.
- `TBankMerchantAPI::buildQuery()` добавляет `TerminalKey` и вычисляет `Token`
  уже после формирования полей. Фильтра полей запроса нет; транспорт — raw cURL.
- `tbank/success.php` трактует `OrderId` как внутренний ID и читает таблицу
  записей WordPress. Поэтому менять только исходящий `OrderId` недостаточно.
- Плагин регистрирует `woocommerce_receipt_tbank` и
  `woocommerce_scheduled_subscription_payment_tbank`: адаптер оборачивает эти
  actions, оставляя оригинальные методы для старых заказов.

## Нумерация

При первом `init` создаётся отдельная InnoDB-таблица
`{prefix}gelikon_order_numbers`. Строка `order_id = 0` содержит счётчик
`next_number = 10000` и границу `legacy_max_id`, зафиксированную один раз.
Все уже существующие заказы, включая старые черновики, остаются со своими
номерами `GL-…`. Их редактирование не назначает новые номера.

Для новых `shop_order` сохраняется соответствие внутреннего ID номеру.
`SELECT … FOR UPDATE` блокирует строку счётчика; повторная проверка соответствия,
вставка номера и увеличение счётчика выполняются в одной транзакции. Уникальные
ключи защищают как номер, так и ID заказа. Повторная обработка не расходует
номер. Ошибка резервирования откатывает счётчик. Удалённые и отменённые номера
не используются снова. Новые checkout-draft получают номер при отправке заказа.

Фильтр `woocommerce_order_number` возвращает новый номер без `GL-`.
Он используется WooCommerce в админке, письмах, личном кабинете, REST API и
на странице заказа. В HPOS фильтр также резервирует номер при первом чтении
`get_data()` после получения внутреннего ID, до `woocommerce_new_order`.
ID записей и AUTO_INCREMENT существующих таблиц не меняются.

## Оплата и уведомления

Для новых заказов фискальные поля собирает оригинальный `SupportPaymentTBank`
с внутренним ID, затем адаптер задаёт новый `OrderId` и свой `NotificationURL`:
`WC()->api_request_url('gelikon_tbank_notification')`.
Подпись рассчитывается по окончательным полям. HTTP выполняется через
`wp_remote_post` с проверкой TLS: клиент из архива отключает проверку TLS.
Используются существующие `merchant_id` и `secret_key` из настроек плагина;
дополнительные ключи не нужны.

Callback проверяет подпись, TerminalKey, сумму, PaymentId и соответствие
номера заказу, затем обновляет заказ через WooCommerce CRUD, включая HPOS.
Блокировка на заказ защищает обработку повторных уведомлений. Все PaymentId
созданных попыток оплаты сохраняются: уведомление от предыдущей попытки
не теряется после повтора оплаты. Повторное CONFIRMED не повторяет завершение
оплаты; позднее REJECTED не отменяет оплаченный заказ. REFUNDED обрабатывается
отдельно. Для подписок сохраняется RebillId с внутренним ID родительского заказа.
Интеграция с установленным WooCommerce Subscriptions отдельно не тестировалась.

## Перед установкой на действующий сайт

1. Сохранить резервную копию БД и развернуть изменение при приостановленном
   оформлении заказов. Первым запросом выполнить `wp eval
   'gelikon_install_order_numbers();'`, чтобы граница старых заказов была
   установлена до возобновления оформления.
2. Проверить, что на данном терминале банка ещё не использовались OrderId
   10000 и следующие номера. Старый плагин отправлял внутренние ID: если старый
   заказ Т-Банка уже имеет ID 10000, использовать его повторно нельзя.
   Адаптер останавливает резервирование при таком конфликте в текущей БД,
   не перескакивает через номер и не меняет старый заказ. Удалённые из сайта
   банковские платежи необходимо проверить отдельно в Т-Банке.
3. Таблицу соответствий и строку счётчика включать в резервные копии.
   Не удалять/сбрасывать их после выдачи первых номеров. При откате темы
   нумерация и платёжная маршрутизация нового типа перестанут работать;
   возвращать старую тему во время незавершённых новых платежей нельзя.
4. Проверить доступ с сервера к `securepay.tinkoff.ru` и доступность нового
   NotificationURL из интернета. Общий URL старых уведомлений в терминале
   не заменять: старые платежи должны сохранить прежний маршрут.
5. Провести оплату в тестовом режиме терминала и проверить OrderId и callback.
   Тесты ниже проверяют сериализованные исходящие запросы, но не являются
   подтверждением живого платежа на банковском терминале.

## Воспроизводимые проверки

```sh
# Существующая облачная среда с WordPress и Docker:
python3 tests/run-order-number-tests.py --compose /workspace/.gelikon-env/compose.yaml

docker compose -f /workspace/.gelikon-env/compose.yaml exec -T wordpress \
  php /var/www/html/wp-content/themes/gelikon/tests/tbank-order-adapter-test.php
```

Runner создаёт отдельные локальные префиксы `gelikon_test_*` для CPT и HPOS,
не изменяет существующие заказы основного сайта и не сбрасывает их счётчик.
Проверяет первые 10000/10001, старые заказы и черновики, настоящий HTML колонки
админки, письма, личный кабинет и thank-you; фактические подписанные тела HTTP
на границе WordPress-транспорта; повтор оплаты, верные/неверные/повторные
callbacks, откат при ошибке БД и сохранение номера удалённого заказа.
В каждом хранилище создаёт 16 заказов параллельно и выполняет 16 параллельных
повторов резервирования одного заказа. Внешние HTTP-запросы теста блокируются,
ответы банка имитируются; настоящие платежи не создаются.
